# 매니저 로그인용 업체 조회

## 한눈에

- **무엇을** 로그인하지 않은 사람이 업체 ID를 보내면, 그 업체가 영업 중일 때 업체 ID · 업체코드 · 업체명을 돌려준다.
- **왜** 프론트가 매니저 로그인 화면에서 업체 ID만 가지고 있을 때, 로그인 · 아이디 찾기 · 비밀번호 초기화에 넣을 업체코드를 받고 업체가 있는지도 확인하려고(2026-11-18 — 업체 ID를 업체코드 자리에 보내 로그인이 404로 실패했다).
- **범위 밖** 프론트 화면 주소(`/manager/[store_code]/login`) · 업체 관리자 등록 SMS · "로그인 주소 복사"는 바꾸지 않는다 — 이 API를 어떻게 쓸지는 프론트가 정한다. 매니저 로그인 API 자체도 그대로다(업체 상태를 보지 않는다 — `apps/admin-service/src/manager/manager.service.ts:101`).

| 진입점 | 한 줄 요약 | 테스트 |
|---|---|---|
| 1. 매니저 로그인용 업체 조회 | 업체 ID → 업체 ID · 업체코드 · 업체명, 없거나 탈퇴면 404, 영업중지면 400 + 정지 사유 | 5건 |

## 1. 매니저 로그인용 업체 조회 — `GET /api/v1/admin-service/store/login-store/:store_id`

**동작 흐름**

1. 받은 업체 ID 그대로(모양은 따지지 않는다 — 로그인도 필요 없다) 지워지지 않은 업체 중에서 찾는다.
2. 없거나 탈퇴한 업체면 "업체를 찾을 수 없습니다."로 거절한다. 모양이 틀린 업체 ID도 찾는 업체가 없으니 같은 404다.
3. 영업중지된 업체면 "영업이 중지된 업체입니다."와 함께 정지 사유를 돌려주며 거절한다.
4. 활성 업체면 업체 ID · 업체코드 · 업체명을 돌려준다.

**입력**

| 필드 | 필수 | 설명 |
|---|---|---|
| `store_id` (경로) | ✓ | 업체 ID(32자 영문 소문자 · 숫자) — 모양이 달라도 거절하지 않고 없는 업체로 본다 |

**결과**

| 상황 | 응답 | 테스트 |
|---|---|---|
| 활성 업체를 조회한다 | 200 `{store_id, store_code, store_name}` | ✓ 정상 |
| 업체 ID 모양이 틀렸다(32자 영문 소문자 · 숫자가 아님) | 404 — 없는 업체와 같은 본문(입력 오류 400 이 아니다) | ✓ 실패 |
| 그런 업체가 없다(지워진 업체 포함) | 404 `{message: '업체를 찾을 수 없습니다.', validation_errors: null}` | ✓ 실패 |
| 탈퇴한 업체다 | 404 — 없는 업체와 같은 본문 | ✓ 실패 |
| 영업중지된 업체다 | 400 `{message: '영업이 중지된 업체입니다.', validation_errors: null, suspend_comment}` — 사유가 없으면 `suspend_comment: null` | ✓ 실패 |
| 게이트웨이를 거치지 않고 서비스에 바로 부른다 | 401 — 서비스 전역 내부 토큰 가드 | — (전역 가드 공통) |

## 결정한 것

- [x] **업체 ID로 찾고 업체코드를 돌려준다.** 사용자 결정 2026-11-18 — 추천안(업체코드로 조회 · 업체코드는 지금처럼 그 업체 사람만 앎) 대신 골랐다. 업체 ID는 업체 둘러보기 API로 누구나 보므로(`libs/contracts/src/discovery/dto/discovery-store-list.dto.ts` 응답의 `store_id`), 이 API가 생기면 업체코드는 사실상 공개 값이 된다. 매니저 로그인을 지키는 것은 비밀번호다.
- [x] **활성만 200, 영업중지는 400 + 정지 사유, 없음 · 탈퇴는 404.** 사용자 결정 2026-11-18("없으면 404 · 정지된 업체는 400 + 사유", 탈퇴는 "404 없는 업체와 같게"). 정지 사유는 업체 컬럼 `suspend_comment`(`libs/database/src/entities/store/store.entity.ts:91`)를 실패 본문의 추가 필드로 싣는다 — 매니저 로그인의 정지 계정 403 + `block_comment`와 같은 방식(`apps/admin-service/src/manager/manager.service.ts:120`).
- [x] **업체 ID 모양이 틀려도 404.** 사용자 결정 2026-11-18("동일한 게 없는 거니"). 그래서 경로 입력 DTO 는 비었는지만 본다(`@IsNotEmpty`) — 형제 업체 상세의 모양 검사(`@Matches` — `libs/contracts/src/store/dto/store-detail.dto.ts:10`)를 두면 ValidationPipe 가 400 을 낸다. 모양이 틀린 값은 그대로 조회돼 결과가 없다(조건은 파라미터로 넘어가 SQL 에 섞이지 않는다).
- [x] **응답은 업체 ID · 업체코드 · 업체명 세 필드만.** 사용자 지정 — 로그인 전 화면에 필요한 것만.
- [x] **admin-service `store` 도메인 · 로그인 없음 · 동기(내부 HTTP).** 쓰는 사람이 로그인 전의 업체 관리자라 admin-service, 대상이 업체라 `store` 도메인(AGENTS.md 서버 · 도메인 규칙). 조회라 큐가 아니다. 경로는 `/login-store/:store_id` — 같은 컨트롤러의 총관리자 업체 상세 `GET /:store_id`(관리자 가드)와 겹치지 않는다.
- [x] **프론트 화면 · SMS · 매니저 로그인 API는 바꾸지 않는다.** 사용자 결정 2026-11-18("너는 그냥 업체 ID로 업체 ID, 업체코드, 업체명 검색 + 없으면 404 해주면 됨"). 프론트 수정 요청 문서에는 이 API만 싣고, 영업중지 업체도 매니저 로그인 자체는 막히지 않는다는 점을 같이 적는다(업체 관리자가 내 업체 화면에서 정지 사유를 본다).
