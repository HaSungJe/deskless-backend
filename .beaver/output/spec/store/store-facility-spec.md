# 업체 편의시설

## 한눈에

- **무엇을** 업체 관리자가 업체 편의시설(편의점 · 카페 · 온천 · 반려동물 동반 · 식사 제공 · 배달 음식 · 주차)을 체크하고, 이용자는 업체 상세에서 보고 업체 검색 필터로 거른다.
- **왜** 지금 편의 항목은 객실 그룹 단위(방 수 · 샤워 · TV · PC)뿐이라 업체 전체가 제공하는 시설로 찾을 수 없다. 뒤이을 AI 대화형 검색(③)이 "온천 · 반려동물 가능 업체" 같은 조건으로 찾을 재료다.
- **범위 밖** 전국 더미 업체(② — 다음 기획), AI 대화형 검색(③ — 그 다음 기획), 총관리자가 업체 편의시설을 고치는 기능, 항목별 설명 · 사진.

| 진입점 | 한 줄 요약 | 테스트 |
|---|---|---|
| 1. 내 업체 편의시설 설정 | 업체 관리자가 편의시설을 통째로 저장한다 | 3건 |
| 2. 내 업체 조회 · 업체 상세(관리) | 업체 관리자 · 총관리자 화면에 편의시설이 보인다 | 0건 |
| 3. 업체 상세(이용자) | 이용자 업체 상세에 편의시설이 보인다 | 0건 |
| 4. 검색 필터 항목 | 객실 · 업체 필터 항목을 한 목록으로 본다 | 1건 |
| 5. 반경 업체 조회 | 업체 편의시설로도 걸러 찾는다 | 2건 |

## 1. 내 업체 편의시설 설정 — `PUT /api/v1/admin-service/store/mine/detail`

**동작 흐름**

1. **내 업체 찾기** — 매니저의 소속 업체를 찾는다(탈퇴 · 지운 업체 제외, 업체 행 잠금).
   - 없으면 → 404 `소속 업체를 찾을 수 없습니다.`
2. **편의시설 채우기** — 보낸 항목은 그 값, 빠진 항목은 없음(0)으로 채워 7개를 모두 만든다.
3. **저장** — 업체의 편의시설을 통째로 바꾼다.

**입력** — 항목마다 0(없음) · 1(있음), 모두 선택(빠지면 없음)

| 필드 | 필수 | 설명 |
|---|---|---|
| `has_convenience_store` | | 편의점 |
| `has_cafe` | | 카페 |
| `has_hot_spring` | | 온천 |
| `is_pet_allowed` | | 반려동물 동반 가능 |
| `has_meal` | | 식사 제공 |
| `is_delivery_allowed` | | 배달 음식 가능 |
| `has_parking` | | 주차 가능 |

**결과**

| 상황 | 응답 | 테스트 |
|---|---|---|
| 일부 항목만 보내 저장한다 | SSE `done`(data 없음) — 보낸 항목은 그 값, 빠진 항목은 없음(0)으로 7개 저장 | ✓ 정상 |
| 소속 업체가 탈퇴 · 삭제됐다 | `failed` 404, 쓰기 없음 | ✓ 실패 |
| 값이 0 · 1 이 아니다 · 모르는 항목을 보냈다 | 400, 필드별 오류 | ✓ 검증 실패 |
| 로그인하지 않았다 · 다른 그룹 토큰 | 401 | — (가드 공통) |

## 2. 내 업체 조회 · 업체 상세(관리) — `GET /api/v1/admin-service/store/mine · GET /api/v1/admin-service/store/:store_id`

2. **편의시설 붙이기** — 응답에 `store_detail`(7개 항목 — 저장 안 된 항목은 없음)을 더해 돌려준다.

**입력** — 지금과 같다

**결과**

| 상황 | 응답 | 테스트 |
|---|---|---|
| 업체 관리자가 내 업체를 본다 | 200, 지금 응답 + `store_detail` | — (엔티티 값 그대로 — 기본값 채우기는 엔티티 훅) |
| 총관리자가 업체 상세를 본다 | 200, 지금 응답 + `store_detail`(보기만) | — (같은 매핑) |

## 4. 검색 필터 항목 — `GET /api/v1/user-service/discovery/detail-filter`

**동작 흐름**

1. **항목 모으기** — 객실 항목(방 2개 이상 · 샤워실 · TV · PC)과 업체 항목(편의시설 7개)을 정의 순서대로 모은다.
2. **목록 반환** — 항목마다 키 · 이름 · 묶음(객실 · 업체)을 돌려준다. DB 는 읽지 않는다.

**입력** — 없음(로그인 없음). 지금의 `GET …/discovery/room-group-detail-filter` 를 대신한다(옛 주소는 지운다).

**결과**

| 상황 | 응답 | 테스트 |
|---|---|---|
| 필터 항목을 본다 | 200, `{list: [{key, name, group}]}` — 객실 4개(`ROOM_GROUP`) 다음 업체 7개(`STORE`), 정의 순서, 빠진 항목 없음 | ✓ 정상 |

## 5. 반경 업체 조회 — `GET /api/v1/user-service/discovery/store`

**동작 흐름**

1. **필터 나누기** — `detail_filter` 의 키를 객실 항목 · 업체 항목으로 나눈다.
   - 정의에 없는 키가 있으면 → 400 `추가정보 필터가 올바르지 않습니다.`
2. **업체 찾기** — 지금 조건(반경 · 활성)에 더해 업체 항목은 그 업체의 편의시설이 있음인 업체만, 객실 항목은 지금처럼 조건을 모두 갖춘 객실 그룹이 있는 업체만 남긴다.
3. **목록 반환** — 지금과 같다(가까운 순 · 최대 300개).

**입력** — 지금과 같다. `detail_filter` 에 업체 항목 키(`has_hot_spring` 등)도 쉼표로 넣을 수 있다.

**결과**

| 상황 | 응답 | 테스트 |
|---|---|---|
| 업체 항목 · 객실 항목을 섞어 거른다 | 200 — 업체 항목은 업체 편의시설 조건, 객실 항목은 객실 그룹 조건으로 둘 다 걸린다 | ✓ 정상 |
| 정의에 없는 항목을 넣었다 | 400 `추가정보 필터가 올바르지 않습니다.`(`detail_filter`), 조회 없음 | ✓ 검증 실패 |

## 결정한 것

- [x] 세 기능으로 나눠 차례로 — ① 업체 편의시설(이 문서) → ② 전국 지역별 더미 업체 → ③ AI 대화형 검색. ③ 은 ①② 가 있어야 추천 결과가 나온다(사용자 결정 2026-11-24).
- [x] 편의시설은 업체 단위 JSON 하나(`t_store.store_detail`) — 객실 그룹 상세(`room_group_detail` · 기본값 상수 · 필터 정의 Record)와 같은 방식이라 항목을 더하거나 빼도 마이그레이션이 없다. 근거: room-group.entity.ts:1 ~ 40.
- [x] 항목 7개, 모두 있음(1) · 없음(0), 기본은 없음 — 편의점 · 카페 · 온천 · 반려동물 동반 가능 · 식사 제공 · 배달 음식 가능 · 주차 가능. 식사는 조식 · 중식 · 석식을 나누지 않고 "식사 제공" 하나, 주변환경(바다 · 산 · 역)은 두지 않는다(사용자 결정 2026-11-24).
- [x] 고치는 곳은 업체 관리자의 내 업체 설정에 따로 — `PUT /mine/detail`(통째로 교체, 영업시간 · 브레이크타임과 같은 PUT). 총관리자는 업체 상세에서 보기만 한다(사용자 결정 2026-11-24).
- [x] 검색 필터는 한 목록으로 합친다 — 새 `GET /discovery/detail-filter` 가 객실 · 업체 항목을 묶음(`group`)과 함께 주고, `detail_filter` 하나에 같이 넣는다. 옛 `room-group-detail-filter` 는 지우고 프론트 수정 요청서로 알린다(사용자 결정 2026-11-24).
- [x] ③ AI 대화형 검색으로 넘기는 결정(사용자 결정 2026-11-24) — ③ 기획 때 그대로 쓴다.
  - AI 모델은 Gemini(Google 검색 그라운딩으로 웹 검색), 업체 정보는 pgvector 벡터 DB 로 만들어 검색한다(Redis 스냅샷은 쓰지 않는다 — 둘 중 하나). 프론트는 백엔드 API 로 붙는다.
  - 로그인 이용자만 쓴다. 이용자마다 대화 간격 30초 ~ 1분(불쾌하지 않으면서 부하를 나눈다).
  - 대화창은 이용자당 1개 — "대화 초기화" 를 하면 새 대화창 ID 로 새 대화를 시작하고 이용자는 그 대화부터 이어 간다. AI 는 대화창 ID 기준으로 이번 요청 + 그 대화창의 이전 대화를 참고해 답한다(다른 PC 에서도 같은 대화를 이어 본다).
  - 대화는 Redis 에 둔다 — 이용자의 대화창(지금 대화창 ID)과 대화창별 대화(이용자 채팅 + AI 답변). 초기화하면 옛 대화창 정보는 Redis 에서 바로 지우고, 그 대화창의 대화 내용은 7일 두었다가 버린다. 주기적으로(scheduler) 7일(24 × 7시간)이 지난 대화 데이터를 지운다(DB 소프트 삭제 규칙은 DB 에만 — Redis 대화는 실제로 지운다).
  - 잡담 벌점 — 숙소 · 여행과 상관없는 잡담은 바로 막지 않고 숙소 · 여행 이야기로 돌리는 안내를 하며 벌점을 매긴다: 잡담마다 1점, 연속 2번째면 +2, 연속 3번째면 +5(연속 3번이면 1+1+1+2+5 = 10점 — 사용자가 적은 식의 +4 는 +5 의 오타로 보았다). 벌점은 이용자별로 지금부터 24시간 전까지의 합(초기화한 옛 대화창 것도 합한다)이고, 10점이 되면 24시간 정지. 벌점은 대화와 따로 Redis 에 둔다 — 기록 한 건이 대화창 ID · 대화(잡담 내용) · 벌점 · 시각이고, 24시간이 지난 벌점 기록은 자동으로 완전히 지운다(합산 기간 밖이라 남길 이유가 없다).
  - 메인 화면의 "가까운 순" 글자는 빼고 AI 검색을 넣는다(프론트 요청서).
  - ③ 기획 때 정할 것: 연속을 세는 기준(사이에 숙소 · 여행 이야기가 끼면 처음부터 다시 센다 — 제안).
